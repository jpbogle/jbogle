Fieldwork

Overview

Fieldwork evaluates whether coding agents can infer unstated requirements while completing real engineering work for large enterprises in private production codebases. The dataset includes 1,000+ tasks spanning full-stack application development, data engineering, SRE and infrastructure, production debugging, and performance optimization. Each environment is a production-ready codebase that lets agents run the application, spin up databases and microservices, use browsers, and test changes end-to-end as a senior engineer would.

Task Creation

Tasks originate from real customer requests and the coding agent sessions used to address them (all using Astra, Fable, or Opus). These sessions required human intervention when agents missed requirements they were expected to infer from the request or codebase: engineers corrected agents, or customers exposed missed requirements. Those corrections shape the task instructions and the verifiers.

Our pipeline brings together the original request, Slack conversations, Granola notes, engineering discussions, PRs, and subsequent feedback to reconstruct a coherent task. It preserves customer context and the engineer’s direction across the work, rather than treating each PR as a standalone problem.

Some instructions are concise, leaving the agent to infer unstated requirements from the codebase:

Make the Equipment Type column editable in the equipment grid without compromising allocation consistency.

Others include the original request and surrounding engineering discussion, leaving the agent to translate that context into a complete implementation:

# Stop phases from being allocated more equipment than they demand

A planner found a phase with 28 generators allocated against a demand of 14,
and nothing in the app stops that. App Allocation on the Equipment page
checks that the phase needs that equipment type at all...

From the thread where we settled what to do:

> I think it makes sense to just block the allocation action if it leads to
> an overallocation … Ya I think we just prevent either action with a note
> explaining over allocation state is not allowed
>
> Don't think it would make sense for the app to choose randomly which
> specific supply to unallocate. I guess u just unallocate some manually and
> then reduce demand

Make this a rule the app enforces: for each equipment type, what is
allocated to a phase must not exceed what the phase's lineups demand. It has
to hold for every way the app changes what is allocated or what...
